# MV2-011 受控本机核对与清退

状态：开发中的操作契约；本文件不代表验收通过，也未执行线上操作。

本机维护权限来自受信运维主机的操作系统身份及部署数据库权限。`actor_id` 是当前数据库中的管理员业务归属，仍核对启用状态和目标角色；不是登录凭据，也不声称已完成网站 MFA。默认仅查看。执行需显式 `--execute` 和 `MARKETING_MAINTENANCE_ENABLED=true`，开关不是身份凭据。命令不监听网络，不接受输入文件覆盖数据库地址。

## 切换顺序

1. 保存当前正式版本、数据库及配置备份，盘点所有共享业务库和同一 Redis 逻辑库的实例、后台任务进程、批量队列及长连接。
2. 停止接收新调用、充值/兑换及账户变动，排空旧请求、任务和进程内待写队列。核对供应商终态及费用；未知费用不能用“已停服务”代替结算。记录停写/隔离依据。不能让新旧资金写法同时服务同一账户。
3. 停止所有旧版本写入者，在独立副本验证本次迁移及来源核对后，按已验证步骤迁移正式数据库。启动不能自动把历史混合余额当作本金。旧营销从未上线，不迁移旧营销表或预览数据。
4. 用维护入口预览正式 New API 历史余额、邀请余额、支付/兑换记录、旧任务和未结请求。结合收款记录和原始操作依据核实来源。已有旧赠送不能伪造成支付；余额为零也不能自动获得“从未充值”资格。
5. 如有旧异步任务，用可信最终费用、终态及原预扣来源核对。当前工具只处理原钱包资金；旧订阅来源需要在切换前按原订阅记录核实排空，不能挪成钱包本金。保留原始期初余额，调整另记证据。
6. 对历史余额执行来源核实，将可核实付费金额与原赠送分开；邀请旧余额明确转为赠金或清退。只有来源核实完成的账户才能开始新调用。已切入新版后的新增账户按正常注册创建来源账本。
7. 全部实例统一新版，再恢复流量。验证新请求、充值/兑换和失败返还均走来源账本。禁止直接恢复旧二进制写入新版数据库；需要回退时先停写、保全新事实，在独立副本拟定数据处理方案，不直接覆盖已发生的消费/支付。

## 本机命令

从运行环境读取 `SQL_DSN`（或既有 `SQLITE_PATH`）与站点设置，不使用另一套收款汇率。

```sh
./new-api marketing-maintenance --input /private/operation.json
MARKETING_MAINTENANCE_ENABLED=true ./new-api marketing-maintenance --input /private/operation.json --execute
```

输入文件必须是当前执行用户拥有、组及其他用户不可读取的普通文件（例如0600）。拒绝符号链接、目录及管道文件；可信标准输入可显式指定 `--input -`。不要在命令参数、JSON证据、工单引用或日志中放 SK、密码、商户密钥或可用认证令牌。证据填可信记录的引用及必要非秘密事实。

执行时使用部署所配置的共享 Redis 及同一逻辑库；缓存无法连接时拒绝执行。数据库提交后刷新该用户及全部 SK（包括软删除记录）的缓存，失败时返回 `cache_refresh_pending: true`，资金操作仍然已经提交。使用同一操作键重放可重试缓存刷新，不重复清退；不要因刷新失败换新操作键。预览不连接或修改缓存。

启用的根管理员可以核对自己的来源和未结请求；其他管理员仍受目标角色限制。清退要求操作者启用、目标账号禁用，因此不能自我清退。初始化根账户的站点赠送属于赠金，不可登记为实际支付或伪造首充。

所有动作都填 `action`、`actor_id`、`user_id`。预览返回资金的站点显示金额、当前版本和未结项目，不写业务表、运行迁移、创建账户或启动后台任务。`inventory` 始终只读。

执行额外填写 `reference`（稳定操作键）、`evidence`、`authorization_reference`、`writer_isolation_evidence`、`currency`。币种必须与当前站点设置一致。相同操作键重复执行返回原操作，不再次清退；异参拒绝，撤权后重试仍拒绝。

| 动作 | 额外输入 | 含义 |
| --- | --- | --- |
| `review-origin` | `expected_balance`、`expected_aff_balance`、`paid_opening_amount`、`gift_opening_amount`、`aff_disposition`、`aff_gift_amount`、`payment_history`、`conversion_evidence` | 来源核实；金额为十进制字符串，零也显式填`"0"`。邀请处理是`none`/`gift`/`clear`。历史支付只可填`unknown`或有依据的`paid`，不能据零余额填`none` |
| `reconcile` | `funding_id`、`version`、`final_amount`、无既有日志投影时的`original_request_id`、`terminal_evidence`、`source_evidence` | 已保存请求的可信最终费用，保留原价格/来源和同一条使用记录。显式零费用也需可信终态，不凭停写免账 |
| `reconcile`（Realtime） | `funding_id`、`realtime_terminal`、`observed_at`、`terminal_evidence`、`source_evidence` | 可信`response.done`及原通知时间；原进程已经停写但未标记连接关闭时，在同一维护事务内记录关闭；按原冻结价格与响应身份重放。其他未知轮或音频仍未结时保留待核对，不强行结清 |
| `reconcile`（正式基线旧任务） | `task_kind`(`task`/`midjourney`)、`task_id`、`expected_task_amount`、`confirmed_net_debit_amount`、`confirmed_user_usage_amount`、原令牌/渠道存在时的`confirmed_token_debit_amount`/`confirmed_channel_usage_amount`、`final_amount`、`terminal`(`SUCCESS`/`FAILURE`)、`terminal_evidence`、`source_evidence` | 核对已有预扣与可信实际费用，差额按原钱包来源处理，不生成充值或营销资格；不支持将旧订阅费用转为钱包 |
| `clear` | `expected_balance`、`expected_revision`、`exact_refund_cny`、`refunded_cny`、`conversion_evidence` | 账号必须已禁用，来源核实且全部请求结清。现金由管理员在支付平台完成后登记；赠金不折现 |

`expected_balance`等钱包金额按站点显示单位输入；`exact_refund_cny`和`refunded_cny`是实际人民币现金，不能从当前展示汇率猜历史可退现金。例如核实人民币1.809元，实退1.81元，保存+0.001元尾差。工具不调用支付平台退款。

## 清零边界

普通禁用账号只阻止所有SK的新调用，不清零、不取消应结算费用。清退前必须等待在途完成。已发生却最终费用未知的请求会阻止清零。

清退注销剩余付费金额、剩余赠金、未使用机会和累计未满档余数；保留充值/消费/签到/抽奖/首充及已领事实。过期赠金记失效，不伪装为消费或现金退款。账号重新启用不恢复旧权益；后续新入账可按原规则获得新奖励。

清退先分批确定旧事件的资格记录（不发放），每批独立授权并留痕，再在最终事务设置全站事实顺序界线。出现“需继续准备资格”时使用相同输入重试；出现余额/版本冲突则重新预览核对，不能盲改期望值。已经成功清退的操作重放不会处理后来产生的新资格。迟到旧事件不会恢复已清退权益。

审计和实际资产变动同事务。数据库/证据/权限错误不等于成功；命令退出码非零时检查原因。Realtime若已记录可信的一轮但仍有其他未知费用，操作可已登记而请求继续待核对，必须预览全部未结项，不能把一次核对成功当作允许清退。

旧任务记录的预扣额不一定仍实际扣着：旧流程可能已返还钱包，却未写回任务标记。维护输入分别确认钱包净扣款、用户用量、令牌扣款、渠道用量，依据各自已入账事实计算差额；不能把任务记录金额直接当作全部来源仍被扣款。各字段包括显式零均需原证据。无限SK可保留历史负剩余计数，不能因此当作钱包负债或免除真实费用。
