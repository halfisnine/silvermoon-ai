## 已观察的失败与边界

1. 首次容量测量所有 HTTP 请求成功，但单账号末尾的账目快照断言失败。服务端响应字节可在结算落库前到达客户端；测试加入有时限的终态／日志排空，再取账本快照，同时保留各项实际值供诊断。首次结果不计为验收通过，原日志保留于 `build/dev/marketing-v2-validation/gateway-capacity-20261124T051146.732100Z.log`。
2. 新恢复测试在 MySQL 首轮失败：批量造用户跨过秒边界，而夹具把统一开始时间当作每个用户的真实注册时间。服务正确拒绝不一致事实。夹具显式固定用户 CreatedAt，与捕获事实一致；没有修改产品的注册时间校验。r1 原记录 `build/dev/mv2-015-20261124T051850.543126Z/` 保留。
3. 完整支付进程回归发现旧测试客户端未传后来已要求的金额配置版本。更新支付／注册测试客户端，从真实管理员 metadata 接口取得 `money_revision` 后再提交付费码表单；不取消服务端的过期配置保护。更新后两套测试通过。
4. 第一次缓存断连验证使用了带短横线的合成 SK，触发既有 SK 附加参数解析，预热即 401；改成符合真实令牌格式的夹具后，两网关真实 TCP 断连及恢复均通过，四笔请求来源、令牌及余额一致。
5. 原有 `HasPendingMarketingRecovery` 的调用者将其解释为未完成模型费用／日志。起初扩展它包含奖励，导致完成模型结算后仍返回“待恢复”的旧合同回归失败。恢复原函数含义，新增奖励恢复查询并仅在调度启用条件组合两者；未修改原测试断言。
