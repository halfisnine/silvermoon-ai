## R2-F01 / P1：OpenAI prompt-only usage 仍被当作完整实际费用

位置：`service/marketing_billing.go:230`；`relay/channel/openai/relay-openai.go:309` 的 fallback 只在 prompt 为零时标记估算。

新的 `confirmedUsage` 判断使用 `HasOpenAIUsageTokens(...) && !estimated`。这个 helper 只能说明“至少有一个非零用量字段”，不能说明当前请求所需的用量已经完整。普通聊天上游返回输出文本 hello，以及 `usage: {prompt_tokens:4,total_tokens:4}`，没有 `completion_tokens`。因为 prompt 非零，不触发本地 fallback 标记，随后把缺失的输出用量当成零费用结清。

独立实际主程序复现：在 r2 的 gateway fixture 中仅将 partial case 从“只有 completion”换成“只有 prompt”，使用单独 PostgreSQL `marketing_v2_r2_partial_audit`、共享 Redis DB13；原 gateway 二进制即 r2 候选。原缺失、流缺失、全零三个场景继续 review；新的 prompt-only 场景失败：

```text
AUDIT_PROMPT_ONLY case=partial-usage state=settled known=true actual=4 reserved=0
panic: estimated usage must retain unresolved funds
```

命令构建 `.dev/run go build -o /artifacts/marketing-v2-validation/r2-partial-audit /workspace/build/dev/mv2-004-r2-partial-audit.go`；运行审查 harness 退出 **2**。证据 `build/dev/mv2-004-r2-partial-audit.log`；源 `build/dev/mv2-004-r2-partial-audit.go`；主程序附属输出使用 `audit-r2-partial-gateway-*.log`，没有覆盖原文件。

修复需要结合接口/协议确认计费维度的完整性，区分字段缺失和显式零，不能仅以非零字段存在认定已知。生成响应有文本但缺输出用量，或只有总量无法划分不同单价输入输出时，保留未知。不能因此把 embeddings 的合法纯输入计费、明确固定按次、已实际测得音频时长/字符的原计价一律打成未知。回归应覆盖两个方向的不完整 usage，以及合法零输出和流式对应边界。

## R2-F02 / P1：Volcengine 单次 TTS WebSocket 已发送，却没有持久发送事实

位置：`relay/channel/volcengine/adaptor.go:333`，`relay/channel/volcengine/tts.go:214`、`:240`。

默认渠道地址+流式语音时 `DoRequest` 返回 nil，随后 `DoResponse` 内进行 WebSocket Dial 和 `FullClientRequest`。这个发送没有经过通用 HTTP 的 `BeginDispatch`。上游接收合成请求后断连，handler 返回错误，而资金会话查不到 dispatch，因此 `Refund` 的 `pre_dispatch_cancel` 成功，错误地认定费用为零并全部释放。

独立真实 WebSocket 与 SQLite 账本复现（调用真实 `handleTTSWebSocketResponse` 和真实 `MarketingBillingSession.Refund`，不是 mock 发送函数）：服务器升级连接、读取一个完整业务请求后直接断开。结果：

```text
AUDIT_SINGLE_TTS_WS accepted=1 dispatches=0 state=settled known=true actual=0 reserved=0
```

执行 `.dev/run go test -overlay /workspace/build/dev/mv2-004-r2-ws-audit-overlay.json ./relay/channel/volcengine -run '^TestAuditVolcSingleTTSAmbiguousDispatch$' -count=1 -v`，退出 0 是**反例成功复现**，不是业务验收通过。证据 `build/dev/mv2-004-r2-ws-audit.log`；overlay 源同目录 `mv2-004-r2-ws-audit_test.go`。原业务源码未改。

这是一次 HTTP 语音合成调用内部使用的上游 WebSocket，不是 MV2-005 的多轮 Realtime。必须在可能产生费用的请求发送前建立持久屏障，明确区分握手失败、发送可能成功、协议终态、负序列完成、用户断开。未知执行不能自动退占用或重发。完整成功仍按字符等原计价来源结算。

## R2-F03 / P1：讯飞普通/流式文本也绕开发送屏障，并把读失败与完成合并

位置：`relay/channel/xunfei/adaptor.go:81`、`:88`；`relay/channel/xunfei/relay-xunfei.go:203`、`:213`、`:225–244`；普通 handler 在 `:200` 返回累计 usage。

`DoRequest` 仅制造 HTTP200 假响应，真实 `xunfeiMakeRequest` 直接 Dial/WriteJSON，没有资金发送屏障。读失败、JSON 失败和 `choices.status == 2` 最终都送同一个 `stopChan <- true`；普通 handler 返回当前累计的 usage，流式 handler直接输出 DONE，却没有写明真实协议终态。于是部分 usage/异常结束不能可靠区分；普通调用可能把非终态累计量结清，写请求失败的路径也可能被当未发送释放。

本项依据逐行代码链核对，**本审查未执行真实讯飞 handler 反例**，不把 Volcengine 的复现冒充讯飞测试。父代理另行只读调查得到相同路径事实。修复后需要本地真实 WebSocket fixture 覆盖请求已送出后断开、部分响应后断开、明确供应商失败及确定终态完成，确保不重发、未知保留、正常费用和令牌守恒。普通/流式文本属于 A01，不能排到 Realtime Issue。
