## F01 / P1：缺失供应商 usage 被适配器补成估算后，新资金会话误标结清

位置：`service/marketing_billing.go:281`；调用链 `service/text_quota.go:563`，上游来源为 `relay/channel/openai/relay-openai.go:185` 和 `:309`。

`RecordMarketingConsumption` 以 `usage != nil` 判断实际费用已知。但 OpenAI 普通响应缺少 usage 时，适配器使用 `GetEstimatePromptTokens()` 和本地输出计数合成非 nil Usage；流正常 DONE 但没有 usage 时同样补算。完整 HTTP 响应/正常 DONE 只能证明响应结束，不能把估算输入数量升级为可信实际用量。现有新会话没有保存用量来源或缺失标记。

独立真实路径复现：复用已构建的主程序，供应商 fixture 不返回 usage，gpt-4o 从 ModelPrice 移除以使用原 token 计价，分别调用两个真实主程序 `/v1/chat/completions` 普通/流式入口。独立 PostgreSQL 库 `marketing_v2_usage_audit`、同一 Redis DB13，不触及开发业务或生产数据。输出：

```text
AUDIT_MISSING_USAGE id=1 state=settled known=true actual=16 settled=16 reserved=0
AUDIT_MISSING_USAGE id=2 state=settled known=true actual=16 settled=16 reserved=0
```

复现源：`build/dev/mv2-004-usage-audit.go`；编译命令 `.dev/run go build -o /artifacts/marketing-v2-validation/usage-audit /workspace/build/dev/mv2-004-usage-audit.go`；执行结果 `build/dev/mv2-004-usage-audit.log`（退出 0，表示复现程序完成，**不是业务验收通过**）。主程序附属日志另存 `build/dev/marketing-v2-validation/usage-audit-gateway-18371.log`、`usage-audit-gateway-18372.log`。

修复应区分可信供应商用量、协议允许且可证明的实际数量、仅为响应兼容/展示生成的估算。未知路径保留待核对事实及占用，不能凭非 nil 或零值对象结清；合法固定按次/图像原计价不应被一律打成未知。覆盖普通、正常结束流、显式零用量与缺失字段，检查其他有本地 fallback 的适配器。回归要经过真实适配器，不能只向 PostTextConsumeQuota 注入 nil。

## F02 / P1：部分请求计价证据不能满足已确认的可恢复要求

位置：`service/marketing_billing.go:43–74`；`pkg/billingexpr/types.go:65` 的 BillingSnapshot 未包含完整请求依赖值。

当前仅保留固定的 n/size/quality 等参数及两个功能请求头。正式表达式契约允许 `param(path)`、`header(key)`；例如 token 费用在实际输出达到某档后使用请求中的自定义数值计费参数，该参数不在白名单时会被删除。预估时可能未进入该分支，因此保存表达式、预估金额/档位并不能反推出原参数。请求中断后，即使拿到可信最终 token 数，仍无法从主库恢复原费用。

独立 overlay 复现（未修改实际源码）：使用项目真实 `RunExprWithRequest` 与 `marketingPricingEvidence`，表达式 `tier("base", c <= 100 ? c : c * param("billing_multiplier"))`，请求参数分别为 2 和 8。两次预估 `c=50` 都得到 50，生成的完整持久计价证据逐字相等；实际 `c=200` 时正确费用分别是 400 和 1600。输出：

```text
AUDIT_PRICING_EVIDENCE_COLLISION identical_saved_facts=true original_actual_costs=[400 1600]
```

命令 `.dev/run go test -overlay /workspace/build/dev/mv2-004-evidence-audit-overlay.json ./service -run '^TestAuditMarketingPricingEvidenceCollision$' -count=1 -v` 退出 0，表示成功证明证据碰撞；日志 `build/dev/mv2-004-evidence-audit.log`，overlay 源 `build/dev/mv2-004-evidence-audit_test.go`。不依赖虚构的未支持表达式，不需要数据库故障即可证明证据丢失；故障/未知用量恢复场景才会实际暴露无法重算的后果。

这不是要求存放提示词、媒体、Authorization 或 Cookie，也不是要求凭空补出供应商未提供的用量。问题是**本站发送前已经掌握且计费依赖的事实**被丢弃了。源码注释及 Issue 进展承认“需要另行取得确认最终金额”，这是实现限制，不能替代冻结 A05 的“主库有足以恢复的终态/定价/来源证据”。供应商通常返回 token/用量，不会知道本站自定义表达式、分组倍率后应扣多少内部金额。

修复应在发送前持久化可安全回放的计费依赖事实/请求表达式的已求值部分；若某种依赖无法安全持久化，需设计明确处理，不能发送后才发现证据缺口。必须继续排除请求隐私和凭证，保持原计价契约。建议验证两份预估结果相同、实际用量跨档后因自定义请求参数不同产生不同费用的请求：移除原内存请求后仍能从持久事实准确重算。

## F03 / P2：用户日志列表和导出顺序不一致

位置：`model/log.go:638`、`:689`。

列表已改为 `created_at desc, id desc`，用户导出仍使用 `id desc`。异步任务延后完成或日志补投时，较早请求具有较大的物理日志 ID；列表显示实际请求时间顺序，导出却把补投的旧请求移到最新位置，而且用户显示序号也随之不同。管理员导出已经使用新顺序，用户导出遗漏。统一列表与导出顺序，并使用请求时间和插入顺序不同的记录验证；现有仅正常顺序样本不能覆盖。
