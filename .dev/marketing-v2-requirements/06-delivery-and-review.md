# 新版开发与验收约束

状态：交付要求，不是已编写或通过的新 Issue，也不是实现架构。

## 分支与参考边界

新实现以核对后的远程 `custom/main` 为基线，使用独立 `codex/` 分支与隔离工作目录。保留旧分支和预览，不覆盖现有未提交文档。

旧营销代码仅参考业务问题、边界与曾发现的缺陷，不能直接复制旧实现或逐个搬提交。先按当前主分支核对事件入口、资金路径、组件与依赖，再编写新版技术方案。主分支现有 New API 能力正常复用，避免同时保留旧奖励入口重复发奖。

主分支未合并旧营销，不意味着生产数据库为空；后续只读核对实际部署/数据后设计主分支到新版的升级。不要凭旧预览表结构设计生产迁移，也不自动导入旧测试营销数据。

## Issue 流程

1. 先保存需求基线，再编写新版技术方案、Issue 与完整验收项，初始全部未完成。
2. 子代理结合四类活动、奖池、资产与退款整体业务评审需求覆盖和验收，不只是检查局部函数。
3. 每个 Issue 整体开发完成后，独立子代理逐项给通过、不通过、未验证及证据。
4. 有未通过项就修复，再对整个 Issue 所有项复验，不能只检查修过的一项。
5. 全项通过才标记完成并 commit，再进入下一个 Issue。
6. 验收标准不得自行弱化或改写；确需调整由子代理评审，涉及业务改变还需用户决定。旧锁文件和旧验收历史不作为新版基线。

## 必须覆盖的验证主题

下列是后续编写 Issue 的覆盖要求，不是已经冻结的验收清单：

- 管理员无需理解内部模型就能配置注册、签到、充值、邀请；用户操作和来源显示一致。
- 管理员与用户的相关金额输入、回显、列表、详情及错误提示均使用站点配置后的金额，不暴露原始 quota 或要求手动换算；实付人民币与账户金额单位明确区分。覆盖不同换算配置、保存再编辑一致性、小额精度和无重复换算，不写死 50000、500000 或 1:1。
- 奖励自动发放、赠金到账生效，无人工审核或手动激活分支；故障恢复不重复发奖。钱包仅显示两类剩余金额，赠金明细有来源、消费、剩余和有效期，底层预扣状态不变成用户操作。
- 每日/连续奖叠加，补签活动总上限跨月不重置，历史目标日资格、不重复档位。
- 五充值玩法区别；实付/到账/赠金分离；跨单累计、多档、重复回调、并发同档；累计比例组合前后端拒绝。
- 兑换码仅付费用途，实际支付记录与在线支付统一首充/累计/活动判断；不新增赠送码分支，同一码重复请求不重复入账或授奖。
- 邀请对象、独立好友累计、实付比例、老关系排除和活动外充值排除。
- 机会发放方式与奖池开奖结果独立配置，四种组合均可，切换方式不得自动修改所选奖池；概率发放适用范围维持充值累计场景，不扩展到其他条件；概率未获机会与使用机会未中奖分开记录，固定赠金不受机会概率影响；机会扣减、防重抽、最后库存并发，未决运营条目关闭后补完整场景。
- 所有赠送入口资产隔离；同步、流式、实时与异步任务全链路原来源记账；账号禁用对新 SK 请求及已有连接的边界真实核验，在途消费正常结算，不强行加入专门退款状态机。
- 用户一次调用只出现一条使用记录，费用旁显示赠金部分，详情展示付费/赠金拆分；调用次数、总金额不因多资金来源重复计算。
- 赠金与付费金额调用范围一致，不新增赠金模型/分组限制，也不绕过账户/令牌原有权限；来源明细可解释组合扣费，退款不把赠金折为现金。
- 故障恢复不重复收款/发奖；多实例共享同一 PostgreSQL 与 Redis 逻辑库，全站约束不能只靠进程内状态或临时 Redis 锁。
- 预计 50–100 并发模型请求，独立测容量、单账号热点与多实例开销，不把测试值当生产承诺。
- 数据库行为变更按仓库规则在真实 SQLite、MySQL、PostgreSQL 检查；迁移覆盖新建与从发布基线升级、重复启动、数据保留。
- 中英文等现有语言、移动端、已有主题、权限与错误提示；涉及鉴权须按项目 OWASP 要求检查。

## 环境与交付

不新增中间件。使用独立开发数据库和 Redis，不共用生产服务；不停止生产，不擅自改线上配置。

前端按项目共享组件和 i18n 规则实施；涉及计费完整阅读计费规范，不因重新开发而取消金额安全、来源或计费测试。发布、推送、PR、部署各自按用户明确任务执行，不能把需求整理等同于发布授权。
